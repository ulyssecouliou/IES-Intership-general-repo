# New maintainer: start here

This is the shortest safe route from a new workstation to useful project work.
The canonical English delivery truth is
`FINAL_TRANSMISSION_RECEIPT_2026-08-28.md`. A detailed French handover is kept
as dated historical context in `HANDOVER_2026-08-28.md`.

## First 30 minutes

1. Obtain GitHub collaborator access from the repository owner.
2. Clone `https://github.com/ulyssecouliou/IES-Intership-general-repo.git`.
3. Check out `main`; it is the canonical/default branch.
4. Read, in order:
   - `FINAL_TRANSMISSION_RECEIPT_2026-08-28.md`;
   - this guide;
   - `AI_USAGE_AND_GOVERNANCE.md`;
   - `../../CLAUDE.md` and `../CLAUDE_REFERENCE.md`;
   - `ARCHITECTURE_AND_RUNTIME_GUIDE.md`;
   - `DATA_EVIDENCE_AND_LICENSING.md`;
   - `TESTING_RELEASE_AND_OPERATIONS.md`.
5. Run `git status --short --branch` and do not start from a dirty tree.
6. If VE campaign reproduction is required, verify and extract the appropriate
   archive from `../../handover/ve_projects/`; never edit the tracked archive.

## Workstation prerequisites

- Windows with IESVE 2025 for real VE/VEScript execution;
- Git for Windows;
- CPython 3.10+ for repository tooling and tests;
- IESVE embedded Python 3.12.3 for scripts launched inside VE 2025;
- dependencies from `pyproject.toml` and
  `scripts/quality/requirements.txt`;
- Microsoft Excel or a compatible viewer for workbook visual QA;
- Outlook or an approved `.msg` viewer for the correspondence archive.

Do not install an AI SDK: the application does not require one.

## Establish a green local baseline

From the repository root, outside IESVE:

```powershell
python -m pip install -r scripts/quality/requirements.txt
python -m pytest -q
python -m black --check --line-length 90 core engine schemas swiss_sia ui scripts tests ve_adapter
python -m flake8 swiss_sia ui scripts core schemas engine ve_adapter tests --jobs 1 --config .flake8
python -m mypy --strict --show-error-codes core schemas
python -m mypy --strict --show-error-codes --exclude '^$' swiss_sia/assessment_governance.py swiss_sia/client_report_context.py swiss_sia/project_evidence_translations.py swiss_sia/value_integrity.py
python scripts/quality/validate_release.py
```

Temporary-directory permission errors in a restricted Windows sandbox are not
application failures. Re-run the suite with an accessible `%TEMP%` before
classifying them.

## Understand the two products

### Client SIA 380/2 technical assessment

- Primary entry point: `Run_VE_Swiss_Compliance.py`.
- Maintained code: `swiss_sia/`.
- Input: the active client VE project, optional APS data and reviewer evidence
  stored under that project.
- Output: technical PDF/XLSX/readiness reports.
- It is not an official certificate and remains fail-closed when evidence is
  absent.

### SIA 4010 software-validation evidence campaign

- Uses disposable exact-case projects and specialised `Run_VE_SIA4010_*.py`
  launchers.
- It must never be run by mutating a client production model.
- Python tests prove software behaviour; VE receipts prove native capability;
  neither alone proves official SIA validation.
- Current per-test status and blockers are in the final handover.

## First half-day inside IESVE

1. Open a disposable or known reference VE project, never a client model first.
2. Run `Run_VE_Swiss_Compliance.py` and confirm the interface opens.
3. Verify EN/FR/DE/IT switching and English default wording.
4. Generate a report from the known model and inspect PDF/XLSX visually.
5. Confirm the report identifies missing evidence instead of manufacturing a
   pass.
6. For SIA 4010, use only the launcher named by the current campaign document.
7. Preserve every JSON receipt generated by runtime capability/read-back probes.

## Where to make changes

| Need | Maintained location |
|---|---|
| Client extraction/report/UI | `swiss_sia/` |
| VE gateway and mutations | `swiss_sia/reference_model/ve_api.py` and bounded adapters |
| SIA 4010 workflows | `swiss_sia/reference_model/sia4010/` |
| Independent reference recomputation | `engine/` + `ve_adapter/` |
| Frozen reference data | `refs/reference-data/` (regenerate; never hand-edit) |
| Evidence templates | `templates/evidence/` |
| Automated tests | `tests/`, `engine/tests/`, `ve_adapter/tests/`, `ui/tests/` |
| Canonical handover/docs | `docs/project/` and `docs/user/` |

`core/` is retained historical/dead architecture unless a specific task proves
otherwise. Do not build new production functionality there.

## Mandatory engineering rules

- Source every normative input and keep its provenance/checksum.
- Missing evidence is never zero, false or pass.
- Capability-check, mutate only when authorised, then read back.
- Use disposable projects for qualification.
- Keep runtime paths relative to the repository or active VE project.
- Keep normative decision logic free of IESVE imports where practical.
- Add a regression test for every resolved defect.
- Do not rewrite shared Git history or publish licensed/client data casually.

## Definition of a safe contribution

A change is ready when the relevant source is identified, tests pass, VE
read-back is captured when required, user-facing text is understandable,
limitations are documented, no unrelated work is included and the commit is
reviewable. A green Python test does not authorise a SIA compliance claim.
