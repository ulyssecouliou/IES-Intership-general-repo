## 4. Technical decision #3 -- We fill the SIA workbook, we do not re-implement it

**Evidence** (`Test1/Resultaterfassung_Test1.xlsx`, sheet `Zusammenfassung Testfälle`):

```
B16 = IF(Daten_Testprogramm!$H$3="Handeingabe"; Daten_Testprogramm!N28; Daten_Testprogramm!F28)
```

The `Testprogramm` columns are **calculated**, never entered manually. `Daten_Testprogramm`
contains two mirror zones: on the left the aggregates derived from the 8760 hours, on the
right (`J:N`) the **manual entry** activated by `H3 = "Handeingabe"`. Averages,
`obere/untere Grenze` and verdicts recalculate automatically.

**Consequences**:

1. The Excel deliverable is the **officially filled SIA form** -- maximum credibility
   with SIA and clients, and zero risk of interpretation divergence.
2. The `engine/` engine recalculates the **same verdicts independently**. Two
   computation paths that agree = the product's quality argument. If they diverge,
   there is a bug, and we know it before the client does.
3. Lowest risk path for the MSP: **`Handeingabe` mode** (aggregates only,
   few cells). Full hourly filling (8760 x N columns) is a later scale-up,
   not a prerequisite.

**Filling: via COM, not via `openpyxl`.** `openpyxl` does not recalculate formulas
and **destroys charts** -- yet these workbooks contain real *chartsheets*
(Test 5 has ~28). Driving Excel via **Pywin32/COM, available in VE**
(section 2), fills `Daten_Testprogramm`, forces recalculation and preserves everything
else. Must be executed **on a copy**, never on the files from `SIA_4010_geteilter_Link/`
which are the frozen source. `⚠ À VÉRIFIER`: the client machine must have Excel installed --
otherwise plan a fallback (XlsxWriter, rebuilt workbook, without the SIA charts).

## 6. Critical path

The bottleneck is not the code (approx. 25% of effort) but:

1. **The VE spike** -- zero lines written to date in `ve_adapter/`, highest
   variance. Deliverable: actual Python version + available packages, and a full
   round-trip *write a construction -> simulate -> read the hourly data -> JSON*.
2. **The example building** (tests 4-7) -- manual modelling from
   `Beispielgebäude/` (IFC abstractBIM + 10 DWG + `Dokumentation_..._V5.pdf`).
   Not parallelisable through code, must be launched independently.
3. **Standards procurement** -- EN ISO 52016-1:2017 blocks the freezing of
   `traceability/test-1.spec.md`. Low cost, high unblocking effect, decision
   outside engineering.

## 7. Process leverage: making the audit executable

`AUDIT.md` cost three manual verification passes on **a single** reference file.
The 1336 cell-to-value comparisons, the label-to-column checks and the
`Streubereich` formula are deterministic assertions -> `engine/tests/`.
`qa-auditor` then audits **the invariants once**, instead of the data at each
regeneration. Without this, audit cost grows linearly with 5 tests x N passes.

Verified state as of 2026-07-30 on `refs/reference-data/test-1.ref.json` (pass 3):
1336/1336 cells matching, 0 label-to-column inconsistency in Table 30 across all
6 cases, Table 32 reduced to 600FF/900FF. Defects #1 and #2 from `AUDIT.md` are
fixed -- but the audit **has not been formally replayed** and the sign-off remains
refused in `AUDIT.md`.

### Initial finding (2026-07-30)

`engine/tests/test_ref_integrity.py` was validated by mutation: four deliberate
corruptions were injected into a copy of the reference JSON.

| Injected mutation | Detected with workbook | Detected **without** workbook (CI case) |
|---|---|---|
| Defect #1 -- column offset (+1), Table 30 | yes | **no** |
| Defect #2 -- phantom case "600" in Table 32 | yes | yes |
| Excel error silently converted to 0 | yes | **no** |
| Wrong `Streubereich` formula (min/max) | yes | yes |

In other words: **CI as configured cannot catch the class of bug that actually
occurred.** The two strongest checks -- value-to-cell fidelity and label-to-column --
require the source, which is absent from the repo (130 MB for the seven workbooks).

Proposed fix, low cost: generate a **raw cell fingerprint** (address
-> value as-is, plus header rows), a few tens of KB, versioned
in `refs/reference-data/`. It is produced from the workbook and re-verified against
it whenever it is present; CI then compares the reference JSON to the fingerprint.
This is not circular: the fingerprint contains the **raw** cells, the JSON contains
their **interpretation** (which programme, which quantity) -- it is precisely
the interpretation that was wrong in defects #1 and #2.
